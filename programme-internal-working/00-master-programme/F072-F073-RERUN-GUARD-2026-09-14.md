## 1 · F072 — same-day workoutId collision on the phone

### 1.1 What was broken

`PhoneRunTracker.swift` builds its wire `workoutId` from either the server-issued canonical id
(`${userId}-${YYYY-MM-DD}`, one per calendar day) or a synthetic `phone_<uuid>`. Two genuine
completions on the SAME calendar day sharing the canonical id — a real second run, or a crash-
recovered completion followed by a fresh one — collided on that id. The backend's completion
endpoint upserts by workoutId-derived row id, so the second POST silently overwrote the first
run's distance and per-phase data. The file's own header comment already named this: *"the
endpoint derives its row id from workoutId and upserts (see route.ts, 'same workoutId → same
id, so re-POSTing overwrites')."*

The Watch fixed this exact bug in production in July (**P1-34**, `2026-07-07`): a `#HHmm`
session-start suffix appended to the wire `workoutId` only, baked in once per completion from
the run's actual start time, with the plan-linkage `workoutId` itself left untouched. The
backend (`web-v2/app/api/watch/workouts/complete/route.ts`) already tolerates the optional
`#HHmm` tail generically, keyed off `body.workoutId` — no source branching, so it was already
correct for a phone-sourced completion the moment the phone started sending a suffixed id.

### 1.2 The fix — copied verbatim, not reinvented

`native-v2/Faff/Faff/PhoneRunTracker.swift`:

1. **New `static func sessionSuffix(for startDate: Date) -> String`** — byte-for-byte the same
   implementation as the Watch's `WorkoutEngine.sessionSuffix(for:)`
   (`native-v2/Faff/FaffWatch Watch App/WorkoutEngine.swift:3408`): `Calendar(.gregorian)` in
   `.current` timezone, `String(format: "#%02d%02d", hour, minute)`.
2. **`buildCompletionPayload`** (the live-finish path) now computes
   `wireWorkoutId = (workoutId ?? "phone_<uuid>") + Self.sessionSuffix(for: started)` and ships
   that in the payload's `workoutId` field, instead of the bare `workoutId`.
3. **`flushInterruptedRun`** (the crash-recovery path) applies the identical suffix, keyed off
   the checkpoint's own `startedAt`, so a jetsam-killed run recovered on relaunch cannot collide
   with a second run started later the same day either.
4. **The stored `workoutId` property itself is untouched** — it stays the plan-linkage key used
   for checkpoint file matching and the `WatchSync` active-session handshake, exactly the split
   the Watch's P1-34 fix made (`workout.workoutId` stays canonical; the suffix rides only on the
   wire payload, minted once from the run's actual start and therefore stable across durable-
   queue retries — never re-minted per POST attempt).

No backend change. `route.ts`'s date-extraction regex (`/(\d{4}-\d{2}-\d{2})(?:#\d{4})?$/`) and
the `runs.id` derivation (`stableBigintFromString(effectiveWorkoutId)`) both key off
`body.workoutId` as sent — traced by reading, not assumed:

- Two completions with the same canonical base and different `#HHmm` suffixes hash to two
  different `stableId` values → two distinct `runs` rows. `ON CONFLICT (id) DO UPDATE` only
  fires when the suffix repeats (a genuine retry of the *same* session), which is exactly the
  intended idempotent-retry behavior.
- `coach_intents`' unique key is `(user_id, reason, field)` with `field = effectiveWorkoutId`,
  so the same distinction holds there.
- A pure-synthetic `phone_<uuid>` id (no date at all) never matches the date-extraction regex
  regardless of the suffix — harmless, since a fresh UUID is minted per session anyway and was
  already collision-free.

## 2 · F073 — post-run flow should not default back into "start this workout again"

### 2.1 The approved spec (verbatim from the dispatch)

1. Default landing after completion = recap/stats, not the workout-start screen, on both
   surfaces.
2. The RUN entry point checks completion state first, using the SAME `after_run` signal
   Today's own screen already reads, before offering today's prescription as startable.
3. A genuine second run is still possible via its own explicit, separate "Just run" action,
   reusing the existing no-goal casual-run mode — never the default.
4. F072's fix stays load-bearing regardless — this is additive, not a replacement.

### 2.2 Phone — point 1 confirmed unchanged, point 2 and 3 implemented

**Point 1 (confirmed, not rebuilt):** `TodayHostV5`'s `legacyContent(_:)` switch
(`HostsV5.swift:1297`) already routes `case .afterRun: TodayAfterV5(...)` by construction —
Today lands on the recap by design whenever `V5Today.state == .after_run`. No change needed;
traced to confirm it is still true on `main`.

**Point 2 — the actual gap.** `RunLobbyV5` (the RUN tab) fetched only `API.fetchWatchWorkout()`
and rendered Start tiles unconditionally — a design-review render on a real completed workout
confirmed the RUN sheet still offered to start it fresh, with no indication anything had
already happened. Fixed in `native-v2/Faff/Faff/ViewsV5/RunLobbyV5.swift`:

- New `RunLobbyCompletionGate.alreadyDone(_ state: V5TodayState) -> Bool` — a small, named, pure
  function (`state == .afterRun`) per this file's own Rule-15 discipline of factoring every
  lobby decision into something testable, rather than an inline comparison buried in the view
  body.
- `loadWorkout()` now also calls `API.fetchV5Today()` — **the exact same call** `TodayHostV5`
  makes to decide `TodayAfterV5` vs `TodayBeforeLiveV5` — and sets `alreadyCompletedToday` from
  its `.state`. No second, independently-derived completion check was invented. A failed read
  here never blocks Start (same posture every other optional read in this file already takes).
- `workoutSection` now checks `alreadyCompletedToday` **before** the existing workout-state
  switch (a workout can load cleanly for a session that's already done — completion, not
  "was a fetch successful," is the gate), and shows a compact "Already recorded" card instead
  of the day's confirmation card. Per Rule 17, this does not re-render the full recap (that
  already lives on Today) — it states the one new fact and points there.
- `startSection` now branches on `alreadyCompletedToday` first: when true, the normal
  Apple Watch / Outdoor / Treadmill tiles are replaced by "Just run" tiles.

**Point 3 — reused, not reinvented.** The phone already has an unstructured-run path (the
`workoutState.hasNoCanonicalWorkout` branch: "Record unstructured outdoors/treadmill," which
records `PendingRunPlanV5.Snapshot.none` and lets the consoles draw their existing no-target
layout). The new `startJustRun(_:)` function reuses this exact mechanism —
`PendingRunPlanV5.shared.record(.none, dateISO:)` then `go()` — deliberately skipping the
re-verification/re-fetch `start(_:)` does, because the whole point of Just Run is that it is
*not* today's prescription regardless of what a fresh read would say. No new casual-run
mechanism was built.

**F072 stays load-bearing (point 4):** `startJustRun`'s doc comment states this explicitly —
recording `.none` is what keeps a genuine second run from being mistaken for the completed one
at the app layer; F072's `#HHmm` suffix is the separate, still-necessary guarantee that even if
this gate were somehow bypassed, the two completions could never collide on the wire.

**Render-verification seam:** added a DEBUG-only `-faffRunCompleted` launch argument
(`RunLobbyV5.forceAlreadyCompletedForRender`), sibling of the already-established `-faffTab`/
`-faffToken`/`-faffHost`/`-faffRunDetail` pattern in `FaffApp.swift` — forces the gate on for a
deterministic screenshot regardless of the signed-in account's actual day. Never compiled into
a release build (`#if DEBUG`).

### 2.3 Watch — points 1 and 2 were already correct; point 3 was the actual gap

Traced `WorkoutRootView.swift`'s `idleHome` router (the Watch's RUN entry point) before
changing anything:

- **Point 1 (already true):** `if let recap = phone.completedToday { V5LobbyRecap(...) }` is
  checked BEFORE the normal `WatchLobbySurfaceV5` start board — today's own session already run
  draws the recap instead of Start, by construction, "checked first, ahead of the stale-plan
  board" per the router's own comment.
- **Point 2 (already true):** `phone.completedToday` is `todayGlance?.completedToday`, sourced
  server-side (`web-v2/lib/watch/build-workout.ts`'s `ranToday`) from **the same week-strip
  completion predicate** `projectWeekStrip` already uses for "did this day happen" — reusing
  the already-loaded row rather than a second completion query, per that file's own comment.
  This satisfies "the same signal," just via the Watch's own already-correct existing wiring
  rather than phone's `V5Today.state`.
- **Point 3 — the actual gap, confirmed by reading `V5LobbyRecap`'s full definition:** it is a
  pure read-only board (distance, duration, pace, rows) with **no action of any kind** — not
  even the "just run" escape every OTHER lobby state in the same file (`V5LobbyRefusal`,
  `WatchRestSurfaceV5`, `PreSessionStalePlanBoard`, `PreSessionFirstLaunchBoard`) already
  offers. Once a session is marked done, the Watch's RUN entry point was a dead end for a
  genuine second run.

**The fix**, in `native-v2/Faff/FaffWatch Watch App/FacesLobbyV5.swift` +
`WorkoutRootView.swift`:

- New `WatchCompletedTodaySurfaceV5` — a two-page `TabView` wrapping the existing `V5LobbyRecap`
  (page 0, the default, unchanged) with the app's **existing** `V5LobbyEscape` component (page
  1) — the exact same "action word + Start button" page every other lobby state's "Just
  run"/"Run anyway" escape already uses, reused verbatim rather than a new casual-run
  affordance. `V5LobbyEscape`'s own header already documents "always the LAST page" — recap
  stays the thing the runner sees first.
- The router's call site now wraps the recap in this surface, wiring
  `onJustRun: { model.start(.makeJustRun()) }` — **the identical call** `WorkoutRootView`'s
  other four escape hatches (`onEscape`/`onPlainRun` on rest day, stale plan, first launch, no-
  session) already make. `WatchWorkout.makeJustRun()` (the Watch's existing no-goal open-ended
  session builder) was reused unmodified.

### 2.4 Scope discipline held

Nothing about workout prescription, pacing, or coaching logic was touched. The only files
changed are the RUN entry point's gating (phone) and the completed-today lobby board's actions
(Watch), plus F072's own file and its tests.
