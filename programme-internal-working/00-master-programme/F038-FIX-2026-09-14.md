## 1 · What was broken, in one sentence

`web-v2/lib/adaptation/canonical-shadow/live-input.ts`'s `buildLiveCanonicalInput` scoped
every BACKWARD-looking read (`weekObservations`, `qualitySessions`, `longRunObservations`,
and their `isCutback`/`authoredPlanMode` witnesses) to `readPlanWorkouts(plan.id)` — the
single currently-active plan's own `plan_workouts` rows — instead of the project's existing
cross-plan-reign-stitched query (`lib/plan/owned-days.ts`'s `ownedDaysSql()`), which already
solves this exact class of bug for `lib/adaptation/load.ts`'s `weekly` query. A calendar week
whose real prescription was authored by a plan that has since been archived and superseded
read as `prescribedMi === 0` — indistinguishable from a week that genuinely predates any plan
— which fed the canonical Adaptation Engine's `WEEKLY_VOLUME`/`LONG_RUN` shadow levers a false
"nothing happened here" on every rebuild.

## 2 · The fix

### 2.1 `web-v2/lib/plan/owned-days.ts` (+25/-1 lines)

Added an opt-in `includePlanWeeks` option to `OwnedDaysSqlOptions` / `ownedDaysSql()`. When
set, the emitted SQL adds `LEFT JOIN plan_weeks pwk ON pwk.id = pw.week_id AND pwk.plan_id =
pw.plan_id` — scoped on BOTH `week_id` and `plan_id` (Rule 14: `plan_weeks.id` is not globally
unique across every plan version, so joining on `week_id` alone could pick up a different
plan's week row) — so a caller can also project `pwk.is_cutback` with the correct per-day
reign attribution. Purely additive: default `false`, zero effect on the existing caller
(`lib/adaptation/load.ts`), verified by the untouched `_owned_days_reign.test.ts` (12 assertions
against the emitted SQL) still passing byte-for-byte.

### 2.2 `web-v2/lib/adaptation/canonical-shadow/live-input.ts` (+159/-24 lines)

1. **New reader, `readOwnedPlanWorkouts(userUuid, fromISO, toISO)`.** Calls `ownedDaysSql()`
   (the pure SQL-string builder — never `loadOwnedDays()`, which issues its query over the
   app's WRITABLE `pool` and would have reintroduced the exact dependency `read-only-db.ts`'s
   header says this directory must not carry) with `includePlanWeeks: true`, executed over the
   fenced `roQuery`. Projects `id, week_id, date_iso, type, distance_mi,
   pace_target_s_per_mi, workout_spec, is_quality, is_long, sub_label` (the same shape as
   `readPlanWorkouts`) plus `owning_plan_mode` (`tp.mode`, the plan that actually reigned over
   that date) and `is_cutback` (`pwk.is_cutback`, that same plan's own week flag).
2. **`buildLiveCanonicalInput` fetches `ownedWorkouts` in the same `Promise.all` as `weeks`/
   `workouts`**, over `[sinceISO, asOf)` — the same 84-day lookback window already used for
   `readRecentRuns`.
3. **The backward-looking half now reads `ownedWorkouts`/`ownedWorkoutsByDate` instead of
   `workouts`/`workoutsByDate`:**
   - `pastWeekStarts` (which weeks even get evaluated)
   - `weekObservations[].prescribedMi` (§3.1 of the scoping report)
   - `weekObservations[].isCutback` — now `pres.some((w) => w.is_cutback === true)`: "trusted
     to say YES, never NO" (per `input.ts`'s own doc comment on the field), so a week spanning
     more than one owning plan (a mid-week rebuild) counts as cutback if ANY owning plan's own
     week said so (§3.2 of the scoping report)
   - `weekObservations[].authoredPlanMode` — now derived PER WEEK from the owning plan(s)'
     `tp.mode`, with the same trusted-YES priority (RECOVERY > TAPER > BUILD) when a week spans
     more than one plan, and `UNKNOWN` (never a silent default to the CURRENT plan's mode) when
     no plan covered any day of that week at all (§3.3 of the scoping report)
   - `buildPrescriptionRunMatches` (prescription↔run identity matching, SUPPLEMENTALGRADE-1)
   - `qualitySessions` and `longWorkouts` (source array)
   - a long run's own following-session check (`nextDayWorkout`, `followingKeySessionOk`) —
     itself a question about what already happened, so it reads `ownedWorkoutsByDate` too
4. **Everything genuinely forward-looking is untouched**, still reading `workouts`/`weeks`
   (`readPlanWorkouts(plan.id)` / `readPlanWeeks(plan.id)`, current-plan-only, per §4 of the
   scoping report): `thisWeekWorkouts`, `nextWeekWorkouts`, `belief.weeklyVolumeMi`/`longRunMi`,
   `plan.nextWeekPrescribedMi`/`nextWeekLongRunMi`/`nextWeekQualityMinutes`,
   `futureThresholdSessionIds`, `nextCutbackBoundaryISO`/`nextRaceBoundaryISO`,
   `substrate.sessions`/`cutbackWeekStarts` (the demand-ceiling model — rule 1's own input, also
   explicitly forward-looking per the scoping report).
5. **`weekly-volume.ts` and `long-run.ts` (the lever files) are untouched** — the scoping
   report confirmed both are pure and already correct; this fix only corrects what is fed to
   them.

No other files were touched. Two new test files were added (§4).
