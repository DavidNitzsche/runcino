6 · A defect I introduced, and how it was caught

My own verification tool ran without its prebuild section and reported CLEAN on a commit CI then rejected. Nothing was wrong with the version on main: the copy I was invoking came from a shared checkout sitting on a stale commit, and amending from there reverted the file to a version predating that section while keeping a newer edit. So several verifications tonight skipped the twenty shipping gates and told me they had passed.

What caught it was the write-barrier ratchet in CI, refusing a proof script of mine that built its own database pool — correctly, since "it only reads" is a property of today's code rather than of the file. That script is now fenced.

My first fix for the tooling gap could never fail: it grepped the script for each section's name, and its own list of names satisfied the grep. That is exactly the gate Rule 18 exists to catch, built while fixing the thing Rule 18 exists to catch. It is replaced, not patched — the check now asserts what actually ran, so a missing section produces no result line and fails.

I am reporting this because a verification tool that is confidently wrong at the moment you rely on it is worse than no tool, and because you should know which of tonight's green results were checked by a short chain. Everything in section 4 has since been re-verified through the full chain.
