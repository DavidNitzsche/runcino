## 6 · A defect I introduced, and how it was caught

My own verification tool ran **without its prebuild section** and
reported CLEAN on a commit CI then rejected. Nothing was wrong with the version on `main`:
the copy I was *invoking* came from a shared checkout sitting on a stale commit, and amending
from there reverted the file to a version predating that section while keeping a newer edit. So
several verifications tonight skipped the twenty shipping gates and told me they had passed.

What caught it was the write-barrier ratchet in CI, refusing a proof script of mine that built its
own database pool — correctly, since "it only reads" is a property of today's code rather than of the
file. That script is now fenced.

My first fix for the tooling gap **could never fail**: it grepped the script for each
section's name, and its own list of names satisfied the grep. That is exactly the gate Rule 18 exists
to catch, built while fixing the thing Rule 18 exists to catch. It is replaced, not patched — the
check now asserts what actually *ran*, so a missing section produces no result line and fails.

I am reporting this because a verification tool that is confidently wrong
at the moment you rely on it is worse than no tool, and because you should know which of tonight's
green results were checked by a short chain. Everything in section 4 has since been re-verified
through the full chain.

## 7 · The visual walk, and why it proves less than I wanted

I walked the app on the current build against a dev server pinned to the read-only role, and probed
every write path first: insert, update and delete on runs, update on plan workouts, insert on coach
intents — all refused with genuine permission denials. The verification client was structurally
incapable of writing your account rather than merely careful.

**But the app had no valid session**, so every screen it drew came from its own
twelve-hour cache. Rule 13 says a display fix is verified by rendering with real data, and a cache
render is not that. So the walk's findings are labelled by what the evidence supports: the status-bar
collision is structural and confirmed; a run-detail screen that appeared to have *no way out*
is observed and not yet called a defect, because the code as written passes a back action.

I did not sign in, because that needs your password. So I built the substrate instead: a local
throwaway database seeded from your real rows, serving the app on the port it already targets, with a
real session row and **no auth bypass added to the app**. It refuses any non-loopback
target before it even reads the credential. Fifteen phone endpoints answer with your real data.

**And then the app would not hold the token.** There is a built-in
debug affordance for exactly this — a launch argument that puts a session token in the Keychain. It
does not work: the app reads the argument, runs its first-launch flow, then sends every request with
no authorization header, and the first 401 fires the session-expired handler, which clears the token
and bounces to the sign-in gate. One 401 destroys the seeded session.

Not a server problem — same token, same server, same moment: no token 401,
bad token 401, walk token **200 with real content**. This is now the highest-priority
phone item, because it is the gate on verifying every other phone fix. While it is broken,
**you are the only person who can render-verify anything on the phone**, and two fixes
are already waiting on it.

The substrate also found a real hole on its way in: the production write barrier judges its target
from an environment variable rather than from the connection a statement is actually issued on. With
that variable pointing at loopback, it would have **permitted a write on a production
client**. Filed to fence it per connection.
