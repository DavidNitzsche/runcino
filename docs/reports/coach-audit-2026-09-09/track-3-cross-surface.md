## 5. `data.type` vs `data.workoutType` — resolved: documented dead-for-display field, live-but-harmless as an internal SQL fallback

Workout B's canonical `runs` row carries `data.type = "easy"` while `data.workoutType = "tempo"`. Resolved directly from `lib/runs/run-shape.ts`'s own doc comments (`[SRC]`), which explicitly name and warn about this exact ambiguity:

- Line 307-311 (`RunData.type`): *"Activity type. MIXED SEMANTICS: 'Run' on Strava-era rows (Strava's activity type) and 'easy' on some faff rows (a workout type). **Do not use this to decide whether a row is a run**; use `sportType`, or the absence of a non-run marker."*
- Line 964-969 (`runTypeSql`, the SQL accessor): the identical warning, verbatim.
- `workoutType` (line 259-271) is the field actually meant to answer "what kind of session was this" — its own doc comment separately documents a Strava-numeric-vs-faff-semantic split and directs callers to `runWorkoutType` rather than reading either field raw.

So `type` and `workoutType` are not two competing answers to the same question — `type` answers "is this a run at all / what was Strava's activity code," `workoutType` answers "what training classification." **Not a live display bug**: no runner-facing composer reads `.type` for a training-classification label (confirmed by tracing `run-purpose.ts`, `run-recap.ts`, `today/route.ts`, and the recap route, all of which key off `workoutType`/`plan_workouts.type`, never `.type`).

**It is, however, a live (and correctly-guarded) fallback inside internal engine SQL**: every call site of `runTypeSql()` (`lib/plan/drift-monitor.ts`, `lib/plan/generate.ts` ×4, `lib/training/decoupling-trend.ts`, `lib/training/durability-anchor.ts` ×2) uses the pattern `COALESCE(runWorkoutTypeSql, runTypeSql, '')` — `type` only wins when `workoutType` is null/absent (a legacy Strava-era row with no faff classification), which is exactly the documented, intended fallback order. For Workout B specifically, `workoutType='tempo'` is populated, so `type='easy'` is never reached by any of these queries. **Verdict: dead for display, alive-and-correct as a documented engine fallback. No cross-surface contradiction results from it.** `[SRC]`

## 6. Post-run "hit" verdict language vs the 49.5%-out-of-tolerance work phase — resolved: doctrine-intentional average-based grading, with a real coverage gap in the follow-on narrative

Traced directly (`[SRC]`) rather than waiting on the pending sub-agent, since the mechanism is fully legible from source:

- The phase `verdict` field itself ("hit"/"fast"/"slow") is computed on the **watch**, in `WorkoutEngine.swift` (~line 1850-1874, `[SRC]`), off the **completed segment's average pace** against the target band — not off the in/out-of-tolerance time ratio. The code's own header comment names the doctrine reason explicitly: *"Research/01 'Pace zone width and lock-in rules' says to judge an interval 'by interval time, not by per-mile pace,' and the segment average IS the interval time expressed per mile. Averaging over the whole rep absorbs the runner's acceleration and the instrument's settling by construction."* For Workout B's single 3.5-mi tempo block, actual average 431 s/mi vs target 430 ± 10s tolerance → correctly, intentionally, "hit." This is not a bug — it is exactly what the doctrine-cited grading rule is designed to do, and average-based grading is defensible precisely because a single average correctly absorbs the kind of mid-rep pace noise a 49.5%-out-of-tolerance timeline can represent.
- The SAME comment block also names where the raggedness goes instead: *"Raggedness still travels, unchanged, as `timeInToleranceSec`/`timeOutOfToleranceSec` — which the server's `winTimeInTolerance` already renders as 'N% of work time inside the target band.'"*
- But `winTimeInTolerance` (`web-v2/lib/coach/run-win.ts:674-690`, `[SRC]`) **requires at least two qualifying work-phase splits** (`if (work.length < 2) return null;`) before it will compose any sentence about tolerance percentage. Workout B's plan is explicitly a **single, unbroken block** — its own authored note says so verbatim ("Single block, no recovery") — so it has exactly one work-phase split, and this composer returns `null` unconditionally for it.

**Net finding:** for a single-block tempo/threshold session (a whole, named workout *shape* in this app's vocabulary, not a one-off), the ~49.5%-out-of-tolerance signal is computed and stored on the row but is **structurally unreachable by the one composer built to speak it**, on any surface, for that entire class of workout. This is not a cross-surface contradiction (nothing says something different elsewhere — nothing says anything about it anywhere), but it is a genuine Rule-15-shaped gap ("a mechanism the corpus cannot reach is untested/unspoken, however correct the rest of the pipeline is") and speaks directly to `docs/ADAPTATION_PROGRESSION_DOCTRINE.md`'s instruction to weigh "physiological cost, late-session deterioration" — not just completion — before crediting a session as evidence pace should move. Recommend flagging to whoever owns `run-win.ts` as a real, scoped finding: either lower `winTimeInTolerance`'s `work.length < 2` floor to also grade a single long work phase's internal ragged-ness, or add a sibling single-phase composer.
