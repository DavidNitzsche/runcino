### 1.2 Bug 1 — "false longest easy run" claim on a tie (TIEFIX-1)

**The defect, on `main` (pre-fix).** `applyRunnerVoice`'s per-week "longest easy run" resolver in `generate.ts` used a bare `>` comparison with no tie detection:

```ts
// main, web-v2/lib/plan/generate.ts (pre-fix)
const best = new Map<number, { mi: number; iso: string }>();
for (const e of flat) {
  if (e.day.type !== 'easy' || e.day.distanceMi <= 0) continue;
  const cur = best.get(e.weekIdx);
  if (!cur || e.day.distanceMi > cur.mi) best.set(e.weekIdx, { mi: e.day.distanceMi, iso: e.iso });
}
```

So two easy days in the same week at the *identical* distance still produce a unique "winner" (the chronologically-first one), and that day's `notes` field prints:

> **"The week's longest easy run. This is where the aerobic volume comes from."**

**[TEST] Direct reproduction against `main`, unmodified `applyRunnerVoice`/`EASY_DAY_ROLE_LINES`.** Fixture: a week with two 6.0 mi easy days (an exact tie) and one 4.0 mi easy day, everything else rest.

```
day0 notes: "Easy enough to talk in full sentences. The week's longest easy run.
             This is where the aerobic volume comes from."
day2 notes: ""   (empty — see note below)
```

Day 0 (6.0 mi) is falsely declared the week's *unique* longest easy run even though day 2 (also 6.0 mi) ties it exactly. (Day 2's `notes` comes back empty because of the separate, correctly-working `BlockScopedSpeaker` de-duplication of the generic "talk in full sentences" standing sentence — day 0 already "said" it for the week, so day 2's `plain`-role line, which is deliberately empty per `EASY_DAY_ROLE_LINES.plain`, has nothing left. This is unrelated to the tie bug and is working as designed.)

**[TEST] Full-corpus scale, via the repo's own archetype generator (`lib/plan/sim-matrix.ts`'s `matrix()`, the same 11,598-archetype cross-product `_sweep_allusers.test.ts` uses).** Walked all archetypes, composed every plan, and counted every week with ≥2 easy days:

                                                     cited "8,781-archetype corpus"
total weeks composed: 99980

**Scenarios 3 & 4 — good execution without progression / poor execution without lost fitness. Verdict: a real, confirmed conflation bug.** Generator: `composeTrainingInfluence()` in `web-v2/lib/coach/training-influence.ts`. **[TEST]** built a fixture — a long-run work phase cut short (`completed:false`) whose actual recorded pace was **470 s/mi, 10 s/mi FASTER than the 480 s/mi planned pace** — and ran the real function chain:

```
SESSION VERDICT: "incomplete"
WORK SUMMARY:    paceSPerMi 470, incomplete true
INFLUENCE OUTPUT: kind "slipping",
  copy: "Long-run pace 0s slow. Endurance signal weaker than the plan calls for."
```

Root cause (`training-influence.ts:107-115`): any session graded `'incomplete'` — a pure *completion* fact (`execution-semantics.ts:515`), independent of pace — is unconditionally routed into `composeSlippingCopy()`, which computes `delta = paceSPerMi - plannedPaceSec`, **floors a negative (i.e., faster) delta to 0** via `Math.max(0, delta)`, and always prints "N s slow" plus "Endurance signal weaker than the plan calls for" / "VO2max stimulus not delivered." **A runner who ran on- or ahead-of-pace but stopped early — injury twinge, time constraint, a deliberate and correct stop — is told a fabricated "0s slow" and that their endurance signal is weaker than planned, when the pace evidence says the literal opposite.** This is the general-case sibling of the WALKBACK-2 defect (scenario 8, below), just uncaught for the session-trajectory surface: "the session ended early" (completion) and "the pace was slow" (measurement) are two different facts, collapsed into one here. By contrast, multi-session cumulative fitness/fatigue language elsewhere in the same file, and ACWR-gated detraining language in `health-actions.ts`, are correctly scoped to repeated evidence, not a single session — so the broader "does one bad session trigger a false fitness-loss claim" question is not otherwise substantiated beyond this specific conflation.

**Scenario 5 — treadmill.** **Verdict: supported, recently fixed.** `run-win.ts#winTreadmill` speaks only in mph/incline-percent, never "pace." **[TEST]** ran `_incline_zero_reading.test.ts` (5/5 passing) — closes a defect from **2026-09-08 (the day before this audit)**: a positive-only incline filter was reading a genuinely-flat (0%) treadmill segment as `null`, which both erased "steady incline" praise on a truly flat run and fabricated it on a belt that actually changed grade. Confirmed both directions now correct via direct execution.

**Scenario 6 — missing pace data.** **Verdict: silent-correctly.** Every pace clause across `run-recap.ts` (7 call sites checked) is ternary-gated on the pace value being non-null; no fallback ever guesses or prints "at NaN:NaN/mi." No *explicit* "no pace data" sentence is spoken either — the app says less rather than stating a refusal outright, which is defensible (Rule 11's spirit is satisfied — no fabrication — even though a stricter reading might want an explicit "don't know" line rather than pure silence).
