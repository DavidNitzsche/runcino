**How to read every evidence claim in this report, added on correction.** Five distinct evidence types recur throughout, and none of them proves what a different one proves — treat these as fixed translations, not caveats to skim past:

- **A "SUCCESS" deploy status proves the deploy landed. It does not prove the deployed feature is correct.**
- **An HTTP reachability probe proves the specific endpoint checked responded correctly to the specific request sent. It does not prove the application is correct beyond that endpoint/request pair.** Where this report cites Railway/production reachability below, the checked surface is `GET /`, `/api/v5/today`, `/api/v5/block`, `/api/races`, and `/api/plan/week`, each confirmed either `200` or the correct `401` for an unauthenticated request — not an exhaustive endpoint list, and stated here rather than as an unqualified "every checked endpoint."
- **Code presence proves the implementation exists. It does not prove it executes correctly at runtime** — this is exactly what the "wired, tested, and inert" pattern throughout this report demonstrates repeatedly.
- **A test count proves the behavior those specific tests actually assert. It does not prove correctness outside what they cover** — Rule 15's own point, applied here to this report's own evidence, not only to the app's.
- **A simulator render proves simulator behavior against whatever data it was fed. It is not physical-device verification**, and per the correction above, no claim in this document should be read as physical-device-confirmed unless explicitly labeled `[Physical]` — no finding anywhere in this report carries that label.

**The structural gap this exhibit confirms (answering the question raised earlier in this process):** this ledger is scoped exclusively to `belief.ts`'s enumerated `BeliefKey` list — 20 fixed, overwhelmingly numeric/physiological quantities, by the file's own design ("No numbers, no thresholds, no physiology. This file names functions" — i.e., it tracks *which function owns the answer*, not the answer's type, but the list of *questions* it watches was itself enumerated from the Runner Model/Training Load/Pace Prescription domains). **A simple yes/no predicate that was never enumerated into `BeliefKey` — such as "is this day sealed," the exact question behind this audit's own 3-site identity-bypass finding (Historical Item 4) — falls entirely outside this mechanism's surveyed scope.** The ledger did not miss that bug through a defect in its own logic; it was never asked the question. This is why the same "one owner" violation class can be rigorously tracked in 20 places and completely invisible in a 21st.

**A second registry exists and was not previously known to this audit: `web-v2/lib/runner-state/quantity-owners.ts`.** Where `ownership.ts` is a static *survey* ("which symbol should own it and which others also answer, and it says so"), `quantity-owners.ts` is a **runtime-executed, numerically-diffing gate**: it names 12 prescription-level quantities (distinct from `ownership.ts`'s 20 belief-level facts — "the quantities a PRESCRIPTION is made of rather than the facts a BELIEF is made of"), and `_owner_agreement.test.ts` actually **resolves every one of them for one real runner on one real date and compares the numbers**, failing on any numeric divergence rather than on a grep. This is a stronger enforcement mechanism than `ownership.ts` for the quantities it covers, and the two registries cross-reference each other by design (e.g., row 5 above points into `quantity-owners.ts`'s `RUNNING_FREQUENCY` entry for the fully-measured version of that disagreement). **Recommendation for future work:** since `quantity-owners.ts` already proves the pattern of executing-and-diffing rather than merely surveying, extending that runtime-diff approach — rather than `ownership.ts`'s static-survey approach — to state predicates like "sealed" is likely the more durable fix for the exact gap this audit found.

## Exhibit E — First physical-device verification of this project, and what it found (added 2026-09-08, second correction pass)

**This is the first physical-device evidence anywhere in this audit's history, and in this project's history as far as this audit's own historical-document sweep could establish (Historical Item 14).** It did not find a clean pass — it found a confirmed defect. Both facts matter and neither should be read as canceling the other: physical verification finally happened, and what it verified is that a real bug exists.

### E1. What David observed, on his own iPhone, against production

Today's UI showed a persistent top banner: *"Can't reach faff. Showing what you had 6 hours ago."* with a Retry control, over a cached Today screen (Tuesday, TEMPO, 6.46 mi / 49:54 / 7:43/mi) that remained usable underneath it.

### E3. What this confirms, and what it does not

**Confirmed — two separate defects, per David's own instruction not to collapse them:**
- **(A) A real backend/production reliability event**: genuine 502s and ~13-second client timeouts across core endpoints. Root cause (application, Railway proxy, database/connection pool, cold start, or another dependency) is **not yet established** — a dedicated investigation was dispatched with an explicit instruction to check Railway/server logs if reachable, and to report `BLOCKED — NO PRODUCTION LOG ACCESS` rather than guess if they are not.
- **(B) A real client-side defect**: after the backend fully recovered (confirmed by the device's own successful requests and its own advancing sync-generation/timestamp diagnostics), the global outage banner did not clear. **This directly falsifies the independent design reviewer's earlier theory** (§Exhibit D10: "a plausible non-defect explanation — a client-side request timeout abandoning the connection before a late response arrives — that would fully explain the symptom without a code fix being needed"). That theory predicted an *invisible* client timeout with no code defect; David's evidence shows the client's *own diagnostics* correctly observed recovery (sync generation advanced, a successful-sync timestamp was recorded) while the *banner* — a separate piece of state — did not follow. That gap between two pieces of client state is itself the defect, and it is visible in the log, not hypothetical.

**Root cause found, confirmed, and fixed in an isolated worktree — not yet merged, awaiting David's approval (§11 decision, added below).**

### E3a. Root cause, exactly (from the dispatched investigation, completed 2026-09-08)

The banner (`StaleBannerV5`) renders whenever `V5Surface<Model>.stale == true`, a flag owned by `native-v2/Faff/Faff/ViewsV5/SurfaceStoreV5.swift`. Before the fix, that file's generation counter (`staleAttemptGeneration`) advanced only at request **completion**, never at request **start** — so it could not tell that an older, slower request had already been superseded by a newer, faster one that succeeded first. Concretely: a slow request (generation N, e.g. David's ~13s timeout) is still in flight; a faster request (N+1) lands and succeeds, correctly clearing staleness; N finally 502s/times out, its `catch` block bumps the counter again and, seeing nothing else happen in its 1.2s debounce window, sets `stale = true` over a screen that is, in truth, fully current. Nothing thereafter retries automatically, so the banner sticks until the runner force-reloads. This exactly matches David's evidence: `PlanSnapshotStore` — the object whose sync-generation/timestamp diagnostics David's log correctly showed advancing — is a completely separate object using a different mechanism (single-flight, not generation-debounce) with **no wiring to `StaleBannerV5` at all**. Two different pieces of client state; one recovered correctly, the other didn't, because the banner was reading the one with the bug.

**A genuinely notable nuance, not previously known to this audit:** this is the *explicitly documented, still-open twin* of a bug (`CANCELBANNER-2`, landed the same day, 2026-09-08) that fixed the *cancelled*-late-loser case and named this *non-cancelled, genuine-failure* case in its own header as a known, undefended gap: *"a genuinely-failed load that lands after a healthy one still raises the banner over current content, indefinitely... a separate, still-open defect and nothing here would notice it."* This was not a hidden bug nobody suspected — it was named, in writing, the same day, and then reported by David from his own phone before anyone picked it up. That is a small, real instance of this project's own "wired, tested, and [a known gap sits] inert" pattern, and also a positive sign: the engineer who landed `CANCELBANNER-2` correctly scoped what their own fix didn't cover.

### E3b. The fix

`SurfaceStoreV5.swift`: the counter (renamed `loadAttempt`) now bumps at the **start** of a load, before any `await`; every completion branch (success, absent, failed, and the timeout `catch`) checks whether its own attempt number is still the latest before applying its result — including the debounce wait, which re-checks after its 1.2s delay in case a newer attempt started during the wait. Net diff: +74/-18 lines, one file.

**Six falsification tests, run against the unfixed code first (Rule 18 discipline, not skipped):** exactly 2 of 6 failed on unfixed code — test 2 (a stale failure completing after a newer success must not resurrect the banner — this is the actual bug) and test 6 (Block, sharing the same `V5Surface` machinery, exhibits the identical bug) — while the other 4 correctly passed already, since they exercise independent, already-correct paths (this is a real falsification, not a vacuous one: a test suite where every test fails "before" would prove nothing about which mechanism is actually broken). After the fix: all 6 pass, all 8 pre-existing `SurfaceCancellationTests` still pass unchanged, and the entire `FaffTests` target — **178 tests** — passes with no regressions. Watch (`/api/watch/today`) confirmed architecturally independent (`WatchSync.swift` holds no `V5Surface`, no `stale` flag, no path into `StaleBannerV5`) — documented explicitly rather than covered by a vacuous test, per the investigation's own instruction not to fake coverage.

### E3c. What remains open

**(A), the real backend 502/~13s-timeout event's own root cause, is still `BLOCKED — NO PRODUCTION LOG ACCESS`** — the investigation found no repo-side evidence (no incident doc, no comment) explaining the specific storm David hit, though `API.swift`'s `StuckConnectionMonitor` (dated 2026-09-04, a documented prior incident: a silently-dead pooled HTTP/2 connection) is named as a plausible, unconfirmed, contributing mechanism. This is disclosed as genuinely unknown, not guessed at.

**Correction to Exhibit D10's original theory, now definitive, not merely "superseded":** the "client-side timeout, architecturally invisible to the app" framing was factually incorrect, and the mechanism is now known precisely — the app's own diagnostics were never blind to the recovery (sync generation and timestamp advanced correctly); the defect was a concrete, ordinary, fixable ordering bug in one file's own state machine.

## Exhibit F — First live-composition evidence for coaching voice, and it resolves part of Product Item 9's standing UNKNOWN (added 2026-09-08, same day)

David sent two real screenshots of his own Today screen showing adjacent days — Tuesday 9/8 and Wednesday 9/9 — both "EASY · 5 mi." Wednesday's Coach's Read asserted: *"The week's longest easy run. This is where the aerobic volume comes from."* This is false as stated: Tuesday ties it at the identical distance. **This is the first real evidence this audit has had on the live-composition half of Item 9 — the half the original report could only mark as a standing, unverified UNKNOWN because the live-account audit is DB-gated and never executes in CI.** It is not a clean pass: the first real check found a real, high-frequency defect.

### F1. Root cause, exact, and far more frequent than a two-screenshot report would suggest

`web-v2/lib/plan/generate.ts:16301-16312`, inside `applyRunnerVoice`: the per-week "longest easy day" walk records a new max only on strict `>`, so a tie silently keeps whichever day comes first chronologically and never records that a tie occurred. `easyDayRole` then renders the "longest easy run" line unconditionally for that one day, with no mechanism to express "tied." **Measured directly against this project's own 8,781-archetype sim-matrix corpus: 62,464 of 98,822 weeks containing any easy day (63%) have two or more easy days tied at the week's maximum distance.** This is not an edge case a runner might occasionally hit — it is the majority shape, and it was invisible to every existing gate because, per a direct check, **no test anywhere asserted the "longest" claim was actually true** before this investigation — the two gates touching this code (`_sentence_repetition.test.ts`, `_layout_contract.test.ts`) check repetition-count and byte-identical output, never content truth. This is the same "wired, tested for shape, never tested for truth" pattern this project's own CLAUDE.md documents repeatedly (the citation-scrub incident, Rule 18's worked examples), now confirmed in the coaching-voice generator specifically.

**Checked, not assumed: no sibling superlative claim shares this bug.** `easyDayRole` has exactly one comparison-based claim ("longest"); its siblings are positional facts, not comparisons. `coach-log.ts`'s "first ever longest run"/"biggest week" claims compare against a *previous best* with strict `>`, where a tie correctly does not constitute a new record — a different, sound comparison shape that does not share this defect.

### F2. The fragmentation complaint — confirmed real, not a doctrine-sanctioned style, and traced to two distinct mechanical causes

Checked directly against `docs/PRODUCT_COACHING_DOCTRINE.md` §30 and CLAUDE.md's own canonical coach-voice examples: doctrine calls for **short, direct, complete clauses** ("That wasn't a good session. Don't chase it tomorrow."), never verb-less fragments. Brevity is doctrine; the specific choppiness David flagged is not. Two distinct, non-doctrinal causes found:

1. **Hand-authored template literals already in the exact shape a prior fix was built to eliminate.** `generate.ts:9022`'s "Easy. Inside the mini-taper for Santa Monica 10k · no quality this close." is the identical fragmented shape the `RUNNERLANG-1` fix's own header names as the defect it exists to kill — but that fix only swaps a list of specific retired phrases, so unrelated hand-authored literals in the same shape (this one, and likely a C-race sibling nearby) were never caught. A copy-edit pass, not an architecture change.
2. **A genuine multi-pass concatenation artifact.** The three-fragment Wednesday paragraph is two independently-authored pieces stitched with nothing but a space: `EASY_DAY_ROLE_LINES.volume` supplies the first two sentences, and a wholly separate strides-appending pass (`generate.ts:8064/8261/8309`) tacks a third sentence on afterward, with no connective tissue between passes. This is a real, if lower-priority, architectural note — how many independent passes append to a workout's `notes` field, and in what order — worth its own scoped look, not bundled into this fix.

### F3. The fix — implemented, falsified, and it uncovered a second, real, pre-existing bug in the process

Fixed in `generate.ts`: the tie-tracker now records whether the current max is contested; a genuinely tied week names no single winner, and `easyDayRole` falls through to the next-sharpest true fact rather than asserting a false uniqueness. Three new falsifying tests (`EASYDAY-TIE-1`) confirmed failing against the unfixed code, passing after; the full `_runner_instruction.test.ts` suite (18/18) and the byte-identical-digest gate (`_layout_contract.test.ts`, snapshot updated with a documented "DIGEST MOVES" entry — plan/day/race-week counts unchanged, only prose text moved) both pass.

**A real, previously-masked defect surfaced by this fix, left deliberately unfixed and disclosed rather than silently patched:** `_sentence_repetition.test.ts` (the Rule 17 "say it once" gate) newly fails with 8 findings once the tie-blindness is corrected — two real 6-day-training-week archetypes (`10k/advanced/35/6d`, `5k/advanced/35/6d`) have two separate easy days that both correctly qualify for the "primer" role ("Short and easy. The session is tomorrow.") and render the identical sentence twice. **The old tie-bug was accidentally masking this**: its buggy tie-break always consumed one of the two candidate days into the "longest" role first, silently removing one of the two "primer" contenders before the repetition gate ever saw them both. Fixing the false-claim bug correctly stopped hiding this second, real Rule-17 collision — this is not a new defect this fix introduced, it is an old one the first bug happened to conceal. **This needs a design decision (promote to one block-level sentence, or pick which day keeps the line) that is outside this investigation's mandate** — added to §11 as a new decision, and the test is left red on the investigation's own branch, not silently patched or hidden, per this project's own Rule 18 discipline.
